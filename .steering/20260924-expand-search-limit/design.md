# 設計書

## アーキテクチャ概要

構成は変えない。`src/data/wikidata-client.js` の定数 `SEARCH_LIMIT` を変更するだけで、検索の流れ(検索 → 詳細の一括取得 → 除外 → 最大7件)はそのまま。

```
wbsearchentities(limit=20) → IDを最大20件
  → wbgetentities(ids=最大20件) → parsePerson で人間かつ生年ありに絞る
  → 検索結果の順で最大7件
```

## 取得件数を20件にする根拠

「織田」で実測した結果(2026-09-24、1回ずつの計測):

| limit | 条件に合う人物 | 詳細取得の応答(gzip後) | 詳細取得の時間 |
|---|---|---|---|
| 10 | 1件 | 約31KB | 約1.6秒 |
| 20 | 10件(7件表示できる) | 約82KB | 約1.8秒 |
| 30 | 18件 | 約111KB | 約1.9秒 |

- 20件で「織田」の候補が7件そろう。11〜20位は織田信秀・信成・哲郎・幹雄・信忠・信孝・長益・信雄・裕二(と氏族1件)
- 30件にしても表示は最大7件のため、増えた分は画面に出ない。一方で応答は約3.5倍になる
- `wbgetentities` のID上限(50件)の範囲内

## データフロー

### UC1: 人物を検索して選ぶ
```
1. 入力が止まってから0.3秒後に検索を開始する
2. wbsearchentities で最大20件のIDを取得する

4. 人間でない・生年がない項目を除き、検索結果の順で最大7件を表示する
```

## パフォーマンス考慮事項

- 詳細取得の応答は約2.6倍(gzip後 約31KB → 約82KB)になる。4G回線でも転送時間の増加は0.1秒程度の見込み
- 「候補の表示: 入力停止から1秒以内」の目標は、limit=10の時点で詳細取得だけで約1.6秒かかっており、もともとWikidataの応答速度に依存している(`docs/architecture.md` の「パフォーマンス制約」)。今回の変更で大きく悪化しないことを手動テストで確認する
