# 設計書

## アーキテクチャ概要

構成・通信は変えない。`person-parser.js` の `parsePerson` に、「人間でない」「生年がない」と並ぶ除外条件として「教育上の観点からフィルタリングする職業を持つ」を追加する。

```
wbgetentities(props=claims) → entity.claims.P106(職業)
  → parsePerson: 人間か → 教育上の観点からフィルタリングする職業を持たないか(追加) → 生年があるか → Person
```

## コンポーネント設計

### 1. person-parser.js

**責務**:
- (追加)職業(P106)に教育上の観点からフィルタリングする職業を含む人物を除外する(`null` を返す)

**実装の要点**:
- 定数を追加する
  - `OCCUPATION = 'P106'`(既存の `INSTANCE_OF` などと同じ書き方)
  - `FILTERED_OCCUPATION_IDS = new Set(['Q1079215', 'Q8380347', 'Q488111', 'Q66382950'])`。各IDにコメントで職業名を付ける
- 関数 `hasFilteredOccupation(claims)` を追加する
  - `claims.P106` が配列でなければ `false`
  - 非推奨(deprecated)ランクを除いた値のうち、1つでも `FILTERED_OCCUPATION_IDS` に含まれれば `true`
  - 生年と違い、職業は「代表の1つを選ぶ」のではなく「すべての値を見る」(人物は複数の職業を持つため)
- `parsePerson` で `isHuman` の判定の直後に `hasFilteredOccupation` を判定し、該当すれば `null` を返す

## データフロー

### UC1: 人物を検索して選ぶ(変更点のみ)
```
1. wbgetentities の各エンティティを parsePerson で変換する
2. 人間でない・教育上の観点からフィルタリングする職業を持つ・生年がない場合は null(候補にしない)
3. 残った人物から最大7件を表示する
```

## エラーハンドリング戦略

- 職業の値の形式が不正な場合(`datavalue` がないなど)は、その値を「教育上の観点からフィルタリングする職業ではない」とみなす。既存の `isHuman` と同じく、オプショナルチェーンで読む

## テスト戦略

### ユニットテスト(`tests/unit/data/person-parser.test.js`)
- 職業に教育上の観点からフィルタリングする職業(AV女優)を含む人物は `null` を返す
- 複数の職業のうち1つでも教育上の観点からフィルタリングする職業なら `null` を返す
- 職業が教育上の観点からフィルタリングする職業でない人物、職業がない人物はPersonに変換される
- 教育上の観点からフィルタリングする職業が非推奨ランクの場合は除外しない

テストデータは既存の `createEntity` で職業のclaimを加えて作る。実在する人物のエンティティは `tests/fixtures/` に保存しない(成人向けの人物のデータをリポジトリに置かないため)。

### 手動テスト
- 「卑弥呼」で候補が0件になり、「該当する人物が見つかりませんでした」と表示される
- 「織田」「豊臣」の候補がこれまでどおり表示される

## 将来の拡張性

- 教育上の観点からフィルタリングすべき職業が新たに見つかった場合は、`FILTERED_OCCUPATION_IDS` にIDを足すだけで対応できる
- 職業が登録されていない人物はすり抜ける。問題が多く見つかった場合は、別の判定方法(所属・ジャンルなど)を検討する
