# 全ドキュメントレビュー

`docs/` 以下の永続ドキュメントをすべてレビューし、各ドキュメントの品質と、ドキュメント間の整合性・重複・齟齬を確認します。

引数: なし(`docs/` 直下の `.md` ファイルすべてが対象)

## 実行方法

```bash
claude
> /review-docs-all
```

## 対象ドキュメント

- `docs/` 直下の `.md` ファイルすべて(例: `product-requirements.md`、`functional-design.md`、`architecture.md`、`repository-structure.md`、`development-guidelines.md`、`glossary.md`)
- `docs/ideas/` は壁打ちのメモで正式な仕様ではないため、レビュー対象外とする。ただし、PRDがアイデアメモの内容を取りこぼしていないかの確認にのみ参照する

## 手順

### ステップ1: 対象ドキュメントの確認

1. `docs/` 直下の `.md` ファイルを一覧にする(`docs/ideas/` は除く)
2. ファイルが1つもない場合は、`/setup-project` の実行を案内して終了する
3. 対象ファイルの一覧をユーザーに示してから、次のステップに進む

### ステップ2: 各ドキュメントの個別レビュー(並列実行)

対象ドキュメント1つにつき1つ、doc-reviewerサブエージェントを起動します。**すべてのサブエージェントを1回のメッセージで同時に起動**してください。

Agentツールを使用してdoc-reviewerサブエージェントを起動してください(ドキュメントごと):
- subagent_type: "doc-reviewer"
- description: "Review [ファイル名]"
- prompt: "[ドキュメントパス]を詳細にレビューしてください。\n\n以下の観点で評価してください:\n1. 完全性: 必要な項目が全て含まれているか\n2. 具体性: 曖昧な表現がないか\n3. 一貫性: 他のドキュメントと整合しているか\n4. 実装可能性: 開発者が迷わず実装できる情報が揃っているか\n5. 測定可能性: 成功指標・性能要件・受け入れ条件が測定可能か\n\n一貫性の確認のため、必要に応じて以下の他のドキュメントも読んでください:\n[対象ドキュメントのうち、レビュー対象以外のパス一覧]\n\nCLAUDE.mdの技術スタックも前提として確認してください。\n\nレビューレポートを作成してください。指摘には必ず箇所(セクション名)を明記してください。"

### ステップ3: ドキュメント横断の整合性レビュー

ステップ2と**同じメッセージで**、ドキュメント横断のチェック専用のdoc-reviewerサブエージェントを1つ追加で起動します。

Agentツールを使用してdoc-reviewerサブエージェントを起動してください:
- subagent_type: "doc-reviewer"
- description: "Cross-document consistency review"
- prompt: 以下の内容

```
以下のドキュメントをすべて読み、個々の品質ではなく「ドキュメント間の関係」に絞ってレビューしてください。

対象: [対象ドキュメントのパス一覧]
前提: CLAUDE.md(技術スタック)、docs/ideas/(PRDの元になったアイデアメモ。参照のみ)

## 確認観点

### 1. 齟齬(矛盾)
同じ事柄について、ドキュメント間で内容が食い違っている箇所を探してください。特に以下を確認:
- 数値: 時間(デバウンス、タイムアウト、表示時間)、件数、年数、サイズ、画面幅など
- 技術スタック・ツール・コマンド(CLAUDE.mdとの食い違いも含む)
- ファイル名・ディレクトリ名・関数名・型名・フィールド名
- レイヤー構成と依存関係のルール
- 画面に表示する文言(エラーメッセージ、表記ルール)
- 優先度(P0/P1/P2)の割り当て
- 状態・ステータスの種類と判定条件

### 2. 追跡性(抜け漏れ)
- PRDの各機能・受け入れ条件・非機能要件が、機能設計書・技術仕様書で扱われているか
- 機能設計書のコンポーネント・ファイルが、リポジトリ構造定義書に配置されているか
- 各ドキュメントで使われているドメイン用語・技術用語が、用語集に定義されているか
- 用語集の定義が、他のドキュメントでの使われ方と一致しているか
- PRDがアイデアメモの重要な内容を取りこぼしていないか

### 3. 重複
- 同じ内容が複数のドキュメントに詳しく書かれている箇所を探してください
- 重複ごとに「どのドキュメントを正(一次情報)とし、他はどう参照に置き換えるべきか」を提案してください
- 役割分担の目安: 何を作るか=PRD、どう動くか=機能設計書、何で作るか=技術仕様書、どこに置くか=リポジトリ構造定義書、どう書くか=開発ガイドライン、言葉の意味=用語集

### 4. 用語・表記の揺れ
- 同じ概念が別の言葉で呼ばれている箇所(例: 人物/偉人、没年不明/没年なし)
- 表記の揺れ(全角/半角、括弧、数字の書き方など)

## 出力形式

以下の形式で出力してください。問題がない観点は「問題なし」と明記してください。

### 齟齬
| # | 深刻度 | 内容 | ドキュメントA(箇所) | ドキュメントB(箇所) | どちらに合わせるべきか |

### 抜け漏れ
| # | 深刻度 | 内容 | 定義元(箇所) | 記載がないドキュメント |

### 重複
| # | 内容 | 重複している箇所 | 正とすべきドキュメント | 他の箇所の扱い |

### 用語・表記の揺れ
| # | 揺れている表現 | 箇所 | 統一案 |

深刻度は [必須](実装を誤らせる矛盾)/[推奨](混乱のもと)/[提案](より良くなる)の3段階です。
```

### ステップ4: レビュー結果の統合と報告

すべてのサブエージェントの完了を待ってから、結果を統合してユーザーに報告します。

1. 個別レビューと横断レビューで同じ問題が指摘されている場合は、1つにまとめる
2. 指摘された齟齬について、該当箇所を実際に読んで事実か確認する(サブエージェントの誤読を報告しないため)
3. 深刻度の高い順に並べる

**ドキュメントの修正は行わない**。報告のみを行い、どれを修正するかはユーザーの判断を待つ。

## 出力形式

```markdown
# 全ドキュメントレビュー結果

## 総合評価

|------------|-------|-------|-------|----------|----------|-----|
| product-requirements.md | [1-5] | [1-5] | [1-5] | [1-5] | [1-5] | [1-5]/5 |
| ... | | | | | | |

## ドキュメント間の齟齬

1. [内容] (深刻度: 必須/推奨/提案)
   - [ドキュメントA](箇所): [記載内容]
   - [ドキュメントB](箇所): [記載内容]
   - 修正案: [どちらに合わせ、どう直すか]

## 抜け漏れ

1. [内容] (深刻度: 必須/推奨/提案)
   - 修正案: [どのドキュメントに何を追記するか]

## 重複

1. [内容]
   - 重複箇所: [ドキュメント(箇所)の一覧]
   - 修正案: [正とするドキュメントと、他の箇所の扱い]

## 用語・表記の揺れ

1. [揺れている表現] → [統一案](箇所: [ドキュメント(箇所)])

## 各ドキュメントの主な改善点

### [ファイル名]

2. [改善点2] (優先度: 高/中/低)

## 次のアクション

- [推奨対応1]
- [推奨対応2]

詳細なレポートは各サブエージェントの出力を参照してください。
```

## 注意事項

- 対象ドキュメント数+1個のサブエージェントを同時に起動するため、数分かかる場合があります
- サブエージェントは独立したコンテキストで動作するため、メインエージェントのコンテキストは消費しません
- 1つのドキュメントだけをレビューしたい場合は `/review-docs [パス]` を使用してください
